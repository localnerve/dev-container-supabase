# New Project Guide — Developing an External Supabase Project Here

This guide walks through taking a **brand-new project** (or the [examples/basic-app](../examples/basic-app) starter) in your projects directory and developing it against a local Supabase stack running inside this workstation. Nothing below is tied to any specific app — follow it once per new project.

## 0. Prerequisites (one-time, per machine)

From this repository's root on the Mac:

```bash
cp .env.example .env            # set PROJECTS_PATH + SSH_AUTH_SOCK for your machine
docker compose up -d            # wait until `supabase-dev-dind` is Healthy
```

Your projects directory (`PROJECTS_PATH`) is mounted read-write at `/workspace` inside the container, so a project on disk and the same path in the container are the *same files*.

## 1. Attach to the workstation

```bash
docker compose exec supabase-dev bash
cd /workspace/<your-project>
```

Inside the container you have Node 24, Bun, the Supabase CLI (3.2.x), Playwright system deps, Xvfb/x11vnc (`xvfb-start`/`xvfb-stop`), and a Docker client pointed at the `dind` sidecar's daemon — so `supabase start` can launch its service containers *and* reach them at `127.0.0.1:5432x`.

## 2. Scaffold the project

Either copy the starter (Bun + TypeScript essentials: strict `tsconfig.json`, supply-chain-guarded `bunfig.toml`, env template, `.gitignore`, an example migration, and a smoke-test entrypoint):

```bash
cd /workspace
cp -r <path-to-this-repo>/examples/basic-app my-new-project   # or work from the Mac side
cd my-new-project
```

…or write your own. The essentials this starter gets you:

| File | Why it's here |
| --- | --- |
| `package.json` | `"type": "module"`, Bun scripts (`dev`/`start`/`typecheck`) — no framework baked in |
| `tsconfig.json` | strict TS, ES2022, Bundler resolution, `@/*` path alias to `src/` |
| `bunfig.toml` | text lockfile + 24h supply-chain guard (`minimumReleaseAge`) |
| `.env.example` | template for `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY` (copy to gitignored `.env.local`) |
| `.gitignore` | env files, `node_modules`, build output, `supabase/.temp/`, test tooling |
| `src/index.ts` | dependency-free smoke test hitting PostgREST at `54321/rest/v1` |
| `supabase/migrations/…` | example first migration (table + seed row) to model your schema on |

## 3. Initialize the local Supabase project state

```bash
supabase init      # creates supabase/config.toml + .env with local defaults/keys
supabase start     # first run pulls ~12 service images into the dind daemon (slow once, fast after)
```

`supabase start` must succeed before anything else — every `supabase status` / app run depends on it. Verify:

```bash
supabase status --output env   # API_URL=..., STUDIO_URL=..., publishable key, ...
```

> Run these from the project directory (one with `.env`). From anywhere else you'll get `Not linked.` — that means "no local stack here", not a broken install.

## 4. Wire up environment variables

- **Local stack defaults** live in the project's `.env` (generated by `supabase init`; contains `API_URL`, `SUPABASE_PUBLISHABLE_KEY`, …).
- **Machine-specific overrides** go in `.env.local` (gitignored) — copy from `.env.example`.

Bun reads neither automatically for your scripts; load them explicitly, e.g. `bun --env-file=.env.local src/index.ts`, or export the vars in your shell before running. The local publishable key comes straight from `supabase status --output env` (or the project's `.env`).

## 5. Apply migrations and run

```bash
bun install
supabase migration up           # applies supabase/migrations/ to the local stack (local is the default target)
bun run typecheck
bun run start                   # the starter prints rows from the items table via PostgREST
```

For new schema work, write a new timestamped file in `supabase/migrations/` (UTC `YYYYMMDDHHmmss_<uuid>.sql`) and re-run `supabase migration up`. `supabase db reset` drops/recreates everything and re-applies migrations from scratch.

## 6. Develop and debug

- **Studio** (schema editor, tables, auth): http://127.0.0.1:54323 — reachable directly from your Mac browser; the stack's ports are forwarded out of the `dind` service.
- **Postgres direct**: `postgresql://postgres:postgres@127.0.0.1:54322/postgres` (binary protocol).
- **Dev email** (MailPit): http://127.0.0.1:54324.
- **Headful browser debugging**: `xvfb-start`, then connect a VNC client to `localhost:5900`; `xvfb-stop` when done. Playwright browsers install per-project into the shared `playwright-cache` volume (`bunx playwright install`).

## 7. Tearing down (and why it's two steps)

```bash
supabase stop                       # stops the service containers
# CLI 3.x keeps project volumes behind; remove them inside dind if you want a clean slate:
docker exec supabase-dev-dind sh -c 'docker volume ls --format {{.Name}} | grep <project-slug> | xargs -r docker volume rm'
```

The workstation stack itself (`dind` + `supabase-dev`) stays up — that's the environment, not your project. From the Mac: `docker compose down` stops it; `docker compose up -d` brings it back.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `Not linked.` + `failed to inspect container health` on `supabase status` | Not in a linked project dir, or `supabase start` hasn't run — see step 3 |
| `supabase start` fails: `error getting credentials - err: exit status 255` | The `dind` service's entrypoint clears a poisoned registry-credential config on boot — if you see this, the container predates that fix; `docker compose up -d --force-recreate dind` |
| Nothing listening on 54321–54324 from the Mac | The local stack isn't started *inside* the container (the forwarded ports are inert until then) |
| `supabase-dev-dind` never becomes Healthy | Docker Desktop daemon is down — `open -a Docker`, wait, then `docker compose up -d` again |
| First `supabase start` takes several minutes | Expected: it pulls all service images into the inner daemon; subsequent starts are seconds |
